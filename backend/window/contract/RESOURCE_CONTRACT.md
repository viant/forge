Canonical resource identity is `window://namespace/name` or `report://namespace/name`. Namespace is logical and never resolves to a network host. An optional `ResourceRef.Revision` requests an explicit immutable stamp; the reserved `working` selector requests mutable content. Omission requires trusted policy selection. The resolved candidate has `Kind`, an actual `Revision` only for stamped content, a distinct byte `ContentFingerprint`, an opaque trusted `AuthorityBinding`, and `ValidUntil`.

Use `identity.ResourceResolver.Resolve` followed by `ReadResolved`. The latter rechecks only the pinned candidate before and after source I/O, verifies bytes, rejects changed principal/account/authority bindings, and caps the current lease to the opened pin. Client bindings, fingerprints, identity claims and expiry values never grant access. Local YAML/JSON has exactly one working candidate and no invented history.

A host activates the canonical existing portable tool paths through `service.PrimitiveProvider.ResourceResolver`. `PrimitiveHostFuncs.DefinitionResolvedFunc` assembles the exact approved bytes; `FetchResolvedFunc` receives the server-approved datasource descriptor plus the resolved fetch input. Both are required. A compatibility `ResourceRefFunc` can map a configured old window key to a canonical logical URI. Once enabled, a legacy `DefinitionRevision` alone cannot execute; that field remains only a compatibility fingerprint, never a revision stamp.

Canonical datasource contracts declare ownership (`provider` or `host`), schema fingerprint, method and any host-owned logical Service alias. Arbitrary MCP methods are supported. Provider connections/credentials remain private. Host aliases require explicit consumer bindings, and `MergeHostBindings` rejects conflicts. Datly descriptors additionally require a component `Kind` (`linked`/`dynamic`), exact `ID`, `Revision`, content fingerprint and schema fingerprint. `ValidateComponentDispatch` checks the actual executable against the approved descriptor; active/latest/working substitution is rejected.

Native MCP `resources/list` and `resources/read` use the same provider/resolver as the existing catalog/definition/fetch tools. Standard list accepts only the standard cursor. Read accepts a logical URI, optionally `?revision=STAMP`; no account/provider/filter parameters are inferred. Tool calls execute pinned approved descriptors with current selected-input authorization before and after dispatch.

Local saved-window hosts install `WithWindowResourceResolver`; optional `WithWindowResolvedDefinitionLoader` receives approved bytes if host assembly is needed. List uses omitted policy selection; get/open uses the explicitly requested selector without first requiring an omitted/default candidate. UI open installs approved inline metadata and a server-held instance pin. Live list/get/context snapshots suppress unbound or no-longer-admitted instances and replace browser resource text with the trusted pin. UI commands require the exact instance ID and `Config.ResolvedWindowAuthorizer` for current action/selected-input admission. `FilterResourceSnapshot` is available to embedding registries that ingest Hub snapshots directly.

Host integration must wire ordinary report/window updates to `SaveWorking` and explicit stamps to `StampWorking`, configure native content validators and revision payload writers, install the operator-controlled resource migration, provide trusted generic policy/identity adapters, and bind datasource dispatch to exact component artifacts. These contracts contain no private IdP vocabulary or endpoint configuration.
